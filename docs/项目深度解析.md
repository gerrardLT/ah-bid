> 解析日期：2026-11-02
> 对象：`d:\project\ah-bid`（公开数据 22,272 公告 / 26.96 GB 附件 / 私有清单 27 项目）
> 方法：读代码 + 直连 `data/index.db` 复算 + 跑项目自带脚本验证

## 〇、结论先行

1. **它的真实形态不是"爬虫"，是三层资产**：公告索引层（可检索）、结构化事实层（评分规则/价格/工期/买家）、交付层（按项目名出技术标三章）。爬虫只是第一层的入口。
2. **技术护城河不在抓取，在"抽取规则"**。整个项目 60+ 脚本里，真正值钱的是 `extract_tender.py` 的三形态评分表提取、`tech-bid.ts` 的物料名还原、`price-benchmark.ts` 的全等匹配——这些规则是几十次踩坑换来的，不可复制。
3. **实测发现 3 个 P0 级问题**：报价口径三套并存且交付物用的是最旧一套；评标办法字段 20.5% 是垃圾值；`fix_method.py` 修复工具已写好但未执行。
4. **文档与数据库已漂移**：至少 6 张表的行数与 RETROSPECTIVE/USAGE 不符，`docs/模型实测台账.md` 的 4 个复现脚本在 `src/` 下不存在。
5. **`scoring_item` 是"宽进严出"设计**：12.76 万行里只有 9.3% 是真评分行，其余是投标人须知前附表。存储层不分类、查询层用 LIKE 过滤，代价是任何人直接查这张表都会被噪声淹没。

## 一、项目到底是什么

```
安徽省公共资源交易平台（ggzy.ah.gov.cn）
        │  省级平台做索引，地市站点做附件（guid 同值，天然对齐）
        ▼
┌───────────────────────────────────────────────────────┐
│ L1 公告索引   22,272 条 · 2026-01~10 · 17 个地区       │
│ L2 附件仓库   10,705 个 / 26.96 GB / SHA-256 全校验    │
│ L3 结构化事实 评分表 127,587 行 · 控制价 1,812 · 中标价 │
│ L4 统计模型   下浮率 / 招标人画像 / 工期分布            │
│ L5 交付物     4 个 Markdown + 4 个 Web 页面            │
└───────────────────────────────────────────────────────┘
```

**一句话**：把"散落在 2 万个公告、1 万个 PDF 里的招投标规则"榨成可查、可算、可直接粘贴的结构化事实。

**不做什么**（设计边界，非能力缺失）：
- 不做 OCR 全量（239 份无评分表的文件里 71% 是低价法，本就没有评分表）
- 不修 `detail_type` 错位 7,994 个（实测 URL 本身就指向招标公告页面）
- 不做履约全量（890/14.3 万，三个字段无区分度）

## 三、七个核心算法

### 3.1 业务分类：证据可复核的加权打分

[classify.ts](file:///d:/project/ah-bid/src/classify.ts) 不是简单关键词命中，有三层设计：

1. **先切"项目本体段"**：定位"建设规模/招标内容"标记后 600 字，并在"招标范围"处截断——否则任何项目都会因罗列专业配套而命中所有类别。
2. **标题 ×3、正文 ×2**，`supporting` 类词（变压器、土建、配电工程）正文须出现 ≥2 次才采信。
3. **primaryTag 按分数取，不按固定优先级**——"输变电工区用房（配套屋顶光伏）"归房建，因为房建证据更重。

每次分类都存 `evidence`（哪个词、在题还是文、几次、多少分），可人工复核。**这是全项目最值得学的模式：结论 + 证据一体落库。**

实测覆盖：building 6,824 / power 873 / pv 599 / storage 135 / 未归类 13,841（62%，设计如此，只做四类）。

### 3.2 评分表三形态提取（技术含金量最高）

[extract_tender.py](file:///d:/project/ah-bid/src/extract_tender.py) 处理三种物理形态：

| 形态 | 识别方式 | 踩过的坑 | 修法 |
|---|---|---|---|
| 表格 | `find_tables()` + 表头含"分值/评分/评审因素" | 跨 2-4 页且续页无表头 | 记住上一表头，同章节列数 ±1、紧邻 2 页内判为续页 |
| 段落 | 编号 + 名称 + （N 分） | 子项嵌在句号后、词被拆到两行 | 边界含`。；分`，先删行内换行 |
| 前附表 | 章节内候选值组合求解 | 单元格只有数字没有"分"字 | 按表头找"分值"列读列值 |

**章节定位的两道防线**（这是数据量翻倍的关键）：
- `is_chapter_head()` 要求章标题在前 12 字符内，且前面不能是"符合/按/见"——否则正文里"符合第二章…"会被当成新章起点，评标办法章节被截成 1 页。
- 起点用"所有真章标题页取并集"，而不是 `body_hits[0]`——后者会命中招标公告里"详见第三章"的引用页。

**结果**：评分行从 46,087 → 127,587（+177%）。

### 3.3 分值构成：三道保险 + 硬约束

只有"合计 = 100（容差 1）"才写入，否则留空：

1. 前附表逐页直取（≥2 项且和 = 100）
2. 章节内候选值组合求解（四项 → 三项 → 两项，覆盖监理类"商务 80 + 技术 20"）
3. 表格"分值"列

**实测覆盖率（观察）**：`score_weights_from_combination` 552 + 前附表 253 = 805 份（40.6%）；`score_weights_not_found` **1,177 份（59.4%）**。这 59% 不是 bug——大量招标文件本就没有四维分值构成（低价法/定性法）。

### 3.4 金额与工期抽取

- 金额：`(招标控制价|最高投标限价|合同估算价|预算金额) + 20 字内 + 数字 + 单位`，保留原文片段。
- 工期：8 种写法（计划工期/合同工期/服务期限/履行期限…），实测只认"计划工期"只能盖住 2/34 份。
- **金额的三层口径**（最痛的教训）：`label` 混了"限价 / 估算 / 预算"三种语义。估算价通常更低，混入会把下浮率系统性高估 1.4 个百分点，所以后来加了 `price_kind` 分层。

### 3.5 下浮率匹配：宁可少配，不可错配

[price-benchmark.ts](file:///d:/project/ah-bid/src/price-benchmark.ts) 的 `norm()`：

```
去空白 → 剥 3 层公告后缀 → 去括号补充说明 → 要求【全等】
再叠加双闸：下浮率 ∈ (-5%, 45%) 且 中标价/控制价 ≥ 0.55
```

历史事故：取前 18 字做 key，把 11,489 万的工程控制价配上了 80.5 万的**监理**中标价，算出 99.3% 的荒谬下浮率。这是全项目最有价值的一次纠错——**错配的数字比没有数字更危险，因为它看起来合理。**

### 3.6 物料名还原（私有清单）

清单列名不可靠：列名"电力电缆"，项目特征里写"名称：电缆头"，740.94 元/m 的"电缆"其实是电缆头。

`realName()` 从 `feature` 里正则取"名称："后的 2~28 字（排除纯字母数字），规格从"规格型号/规格/型号"取。这是私有数据能用的唯一原因。

### 3.7 报价模拟器（Web 层）

[simulator.html](file:///d:/project/ah-bid/web/simulator.html) 的决策链：口径选择 → 基准优先级（招标人 > 评标办法 > 档位×类型 > 同类型 > 同档位 > 全局）→ 修正项 → 置信度。

**核心发现（观察，来自 docs/模型实测台账.md）**：招标人是最小解释单元——组内离差 2.7 vs 全局标准差 9.3（0.29）；跨城市招标人 0 个（完全嵌套）。所以"黄山下浮低"是假象，实际是当地招标人"价格硬"。

## 四、实测发现的问题

### P0-1 报价口径三套并存，交付物用的是最旧一套

同一件事（安徽工程下浮率），项目里有三套数字：

| 来源 | 样本口径 | 总体中位 | 房建中位 |
|---|---|---|---|
| **A. `tech-bid.ts` 硬编码**（用户拿到的 03-报价基准.md） | 未标注，无"其他"类 | **18.1%** | **19.5%** |
| **B. `price-benchmark.ts` 实算**（本次复跑） | 仅 `price_kind='限价'`，437 条 | 16.7% | 17.7% |
| **C. `docs/模型实测台账.md` v3** | 限价 370 + 估算 1,248，按口径分层 | 15.0%（混合） | 16.7%（混合） |

**证据（观察）**：
- 本次执行 `node src/price-benchmark.ts --out=data/_pb.md`，输出 `平均 18.9% / 中位 16.7% / 四分位 11.9%~29.4%`，与 RETROSPECTIVE.md 一致，与 tech-bid.ts 的 `20.3% / 18.1% / 13.0%~30.5%` 不一致。
- tech-bid.ts 第 136-159 行是纯字符串硬编码，无来源、无日期、无样本量。

**影响**：控制价 5,000 万的项目，按 A 报 3,985 万，按 C（混合）报 4,250 万，差 **265 万**。而 RETROSPECTIVE 5.3 自己写过"一个点就够决定中标与否"。

**修法（2 小时）**：tech-bid.ts 不要硬编码，改为调用 `price-benchmark.ts` 的同一个匹配函数，输出带 `n / 口径 / 日期`；口径默认按 `tender_price_raw` 的城市推断（caliber.json 已有三套系数）。

> ✅ 已修复（2026-11-02）：抽出 `src/lib/price-stats.ts` 作为唯一实现，tech-bid 改为三口径实算并支持 `--caliber`。见第九节。

### P0-2 评标办法字段 20.5% 是垃圾值

**证据（观察）**：`tender_doc.evaluation_method` 有 **58 种不同字面值**，归一化后：

| 归一化类别 | 条数 | 占比 |
|---|---|---|
| 综合评估法/综合评分法 | 1,222 | 61.7% |
| **其他/垃圾** | **406** | **20.5%** |
| 合理价格法类 | 169 | 8.5% |
| 定性定量法类 | 135 | 6.8% |
| 最低价法类 | 48 | 2.4% |
| null | 2 | 0.1% |

垃圾值样本：`”规定的方法`(259)、`本招标项目评标办法`(97)、`中方法`(5)、`及定标办法`(3)、`第三章 评标办法`(2)。另有 `（综合评估法`(196)、`采用综合评估法`(43) 等带前缀未清理的，导致同一方法被拆成 8 个 key。

**根因**：`METHOD_PATTERNS` 第 2 条是宽松正则 `(?:评标办法|评标方法|评审办法)\s*[：:]?\s*[^\n。；、，.]{0,16}?法`，会命中正文引用句。

**影响**：`docs/模型实测台账.md` 的 f₂ 评标办法系数（综合评估法 27.4% / 低价法 16.7% / 合理价格法 6.0%）建立在未归一化的字段上，20.5% 样本被静默丢弃；若垃圾值里混有低价法，系数会被稀释。

**修法（两步，约 1 小时）**：
1. **跑已写好的修复脚本**：`python src/fix_method.py`（幂等，只改含"规定的方法"的行，259 条）。注意它会将抽不到的置 NULL——这是正确的"诚实表示"。
2. 补一个归一化函数，把 58 种字面值收敛到 6 类（去 `（`/`采用`/`本项目`/`：`/`”` 前缀 + 关键词映射），写入新列 `evaluation_method_norm`，建模只用这一列。

> ✅ 已修复（2026-11-02）：直接清洗原列而不是新增 norm 列（下游只有一个消费方，多一列反而多一处口径）。垃圾值 406 → **0**，字面值 58 → **24**。见第九节。

### P1-1 发布日期被项目编号污染

**证据（观察）**：3 条公告 `pub_date = 2026-32-05 / 2026-32-03`：

```
安徽省肿瘤医院…二期工程室外土石方工程项目
（项目编号：2026DFAGZ00410/JG2026-32-0579）中标结果公示
```

`parseListHtml` 用 `/(\d{4}-\d{2}-\d{2})/.exec(block)` 在整块 HTML 里找**第一个**日期，标题里的项目编号 `JG2026-32-0579` 中 `2026-32-05` 正好匹配。

**影响**：按月统计多出一个 "2026-32" 月份；`max(pub_date)` 返回 `2026-32-05`（字符串排序），任何"数据最新到几月"的判断都会错。

**修法（30 分钟）**：日期正则锚定到列表项的日期 DOM 节点，或加 `(0[1-9]|1[0-2])-(0[1-9]|[12]\d|3[01])` 约束；再补一条 `CHECK` 或清洗 SQL 修 3 条脏值。

> ✅ 已修复（2026-11-02）：正则加合法月/日约束；3 条脏值置空（附件路径里没有可推断的年月）。见第九节。

### P1-2 `scoring_item` 91% 是无关行

**证据（观察）**：127,587 行中，含评分关键词（分值/得分/评分标准/评分因素）的 11,840 行（**9.3%**），含废标关键词的 3,472 行（2.7%）。其余 88% 是投标人须知前附表（开标程序、文件递交等）。

**这不是 bug，是设计**：`extract_scoring_tables` 收录章节内所有列数相近的表格（为了不漏），`tech-bid-scoring.ts` 再用 LIKE 过滤。代价：
- 任何人 `SELECT * FROM scoring_item` 都会被噪声淹没；
- 过滤条件是 4 个 LIKE 字符串扫描，全表查一次要扫 12.7 万行 JSON 文本；
- 文档里的"12.3% 真评分表"已降到 9.3%，因为后来 1,982 份里包含更多长文件。

**修法（3 小时）**：抽取时给 `scoring_item` 加 `kind` 列（`score` / `reject` / `other`），入库时一次判定，查询零成本。`tech-bid-scoring.ts` 可删掉 30 行 LIKE 条件。

### P1-3 `score_technical = 5.0` 出现 159 次，疑似误抽

**证据（观察）**：技术标分值分布 top5：`5.0`(159) / `30.0`(85) / `15.0`(51) / `20.0`(47) / `40.0`(36)。

"5 分"是符合性评审里"技术标符合要求（5 分）"的典型写法，不是技术标总分。而 `_combine()` 只要求"合计 = 100"，若某文件候选值里恰好有 `技术 5 + 商务 80 + 报价 15`，就会被当成合法解。

**推断**：这 159 份的商务/报价分值可能被错误抬高。需要抽样 10 份对照原文。

**修法**：`_combine()` 加业务约束——技术标分值 < 10 时，要求同时命中"符合性/合格"语境才采信，否则回退到 `score_weights_not_found`。

### P2-1 Web 浏览器漏了 3 张核心表

**证据（观察）**：[server.py](file:///d:/project/ah-bid/web/server.py) 的 `GROUPS` 白名单共 24 项（21 表 + 3 视图），但库里还有 `tender_buyer`(8,188)、`tender_duration`(7,899)、`tender_price_raw`(7,352) 三张表不在白名单——**恰好是 v3 定价模型的全部底座**。前端看不到，只能命令行查。

**修法（10 分钟）**：GROUPS 加一组 `("招投标画像", ["tender_buyer", "tender_duration", "tender_price_raw"])`，`LABELS` 补三个中文名。

## 五、值得复用的工程方法

| 模式 | 具体做法 | 为什么值钱 |
|---|---|---|
| **宽进严出** | 存原文全量（`body_text`、`scoring_item`），查询层再过滤 | 换关键词不用回源重抓，22,272 条正文可离线重跑分类 |
| **结论带证据** | 分类存 `evidence`，标准存 `sources`，调研存 `why` | 一年后还能回答"当初凭什么这么判" |
| **先小样本否证，再全量** | OCR、detail_type、履约全量：都是先花几小时验证，再决定不做 | 三次"不做"省下的时间 > 做错的数据 |
| **失败隔离 + 断点页级** | `crawl_failure` 表 + `crawl_state` 页级断点 + `--retry-failed` | 6 小时任务中断不用从头再来 |
| **硬约束代替猜测** | 分值构成必须合计 100，否则留空 | 宁缺勿错，空值可人工补，错值会静默传播 |
| **全等匹配代替前 N 字** | 下浮率匹配 | 错配的数字看起来最合理 |
| **限速串行** | 全局 1.5s 间隔，绝不并发 | 快一点就返回假成功页，制造无声缺失 |
